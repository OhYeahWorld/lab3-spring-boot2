# Лабораторная работа №3 — Java Spring Boot + PostgreSQL

Проект сделан по приложенному заданию. В ТЗ указаны три таблицы `saldo`, `charges`, `payments`, WEB-интерфейс для их заполнения и три отчетных модуля на основе хранимых процедур; в приложенном файле также есть образцы трех сводок: годовая оборотная ведомость, ведомость по квартире и сводка должников.

## Что реализовано

В БД остаются **ровно три бизнес-таблицы**: `saldo`, `charges`, `payments`.

Для каждой записи хранится:

- `created_at` — когда запись создана;
- `updated_at` — когда запись последний раз изменена.

Записи нельзя дублировать. Проверка выполняется в Java и дополнительно ограничениями PostgreSQL. Для начисления и платежа учитываются именно видимые для пользователя реквизиты, поэтому изменение `description` или номера-ссылки не позволяет создать вторую одинаковую строку.

Сальдо считается по формуле:

`исходящее = входящее + начисления - платежи`.

Для квартиры цепочка периодов поддерживается автоматически: входящее сальдо следующего сохраненного периода равно исходящему предыдущего. При изменении/удалении начисления или платежа все уже существующие последующие периоды пересчитываются; новые недостающие записи приложение не создает.

## Главное исправление запуска PostgreSQL

В предыдущем варианте схема и функции запускались через обычный `schema.sql`, а демонстрационные данные лежали отдельно в `db/demo-data.sql`. Из-за этого приложение могло стартовать пустым, а часть страниц обращаться к отсутствующим функциям.

Теперь `schema.sql` и `data.sql` автоматически выполняются самим Spring Boot-приложением через JDBC еще до того, как приложение начинает принимать WEB-запросы. Это сделано намеренно: в `schema.sql` есть тела PostgreSQL-функций с внутренними `;`, поэтому простой Spring-скриптер здесь не используется. После успешного запуска данные сразу появляются на страницах.

## Запуск PostgreSQL

В проекте PostgreSQL 17, потому что для PostgreSQL 18 официальная структура каталога данных Docker была изменена; в прошлой конфигурации использовался путь старого формата для образа 18. Текущая конфигурация использует совместимую для этого проекта схему volume.

Запуск:

```bash
docker compose up -d
```

Проверить контейнер:

```bash
docker compose ps
```

БД:

- database: `lab3`
- user: `lab3`
- password: `lab3`
- host: `localhost`
- port: `5432`

## Если ты уже запускал старую версию проекта

Для учебной БД, которую можно пересоздать, лучше один раз удалить старый volume, чтобы не остались старые таблицы/триггеры:

```bash
docker compose down -v
docker compose up -d
```

После этого запускай Spring Boot. Никакой ручной загрузки SQL больше не нужен: приложение само создаст структуру БД и загрузит демонстрационные записи только в полностью пустую БД.

## Запуск приложения

Требуется Java 21+ и Maven 3.6.3+.

```bash
mvn clean spring-boot:run
```

Или собрать JAR:

```bash
mvn clean package
java -jar target/accounting-lab3-1.0.0.jar
```

Открыть:

`http://localhost:8080`

Подключение к другой PostgreSQL можно изменить переменными:

```text
DB_URL=jdbc:postgresql://localhost:5432/lab3
DB_USER=lab3
DB_PASSWORD=lab3
```

## Страницы

- `/data/saldo` — заполнение сальдо;
- `/data/charges` — заполнение, изменение и удаление начислений;
- `/data/payments` — заполнение, изменение и удаление платежей;
- `/reports/turnover?year=2017` — оборотная ведомость за год;
- `/reports/apartment?apartment=1&year=2017` — начисления и платежи по квартире;
- `/reports/debtors?asOf=2017-10-01` — должники по категориям.

## Три хранимые функции

В `schema.sql`:

- `sp_turnover_statement(year)` — годовая оборотная ведомость;
- `sp_apartment_statement(apartment, year)` — начисления и платежи по квартире;
- `sp_debtors_summary(as_of)` — сводка по категориям должников.

Именно их вызывает `ReportRepository`.

## Что взято из образцов на фотографиях

На первой фотографии показаны конкретные помесячные значения для квартир 1–6; именно они перенесены в `data.sql`. На второй фотографии приведен отдельный пример ведомости по квартире с другими исходными данными. Его число `3500.70` для поля «+ долг/-переплата (за пред. период)» текст ТЗ не определяет формулой, поэтому приложение не придумывает для него скрытые данные и явно показывает вычислимые поля по имеющейся базе. На третьей фотографии присутствуют квартиры 12 и 14, но исходные начисления/платежи для их построения в приложенном ТЗ не приведены; поэтому скрытые операции для них в базу не добавляются.

## Данные из изображений задания

Из годовой ведомости перенесены показанные значения для квартир 1–6 за январь–октябрь 2017. Ноябрь и декабрь **не создаются**, потому что в исходной таблице для них стоят нулевые значения и это не является основанием придумывать реальные записи в БД.

Проверены цепочки сальдо. Например, для квартиры 1:

`5379.37 + 4590.22 - 4004.06 = 5965.53`,

а февраль начинается с `5965.53`.

Такая же проверка выполнена для всех десяти месяцев по шести квартирам; значения из изображения сверяются с формулой сальдо.

В отчете незаполненные месяцы показываются как нулевые значения **без создания записей в таблицах**.

## Что было исправлено относительно первой версии

1. Убрано использование стандартного Spring SQL-скриптера; `schema.sql` выполняется целиком через JDBC до приема WEB-запросов.
2. Автоматическая загрузка демо-данных встроена в запуск приложения: только если все три бизнес-таблицы пустые. При наличии хотя бы одной записи повторная загрузка не выполняется.
3. Исправлена Docker-конфигурация PostgreSQL.
4. Убрана причина падения страниц `/data/*`, связанная с использованием `#fields` вне контекста формы.
5. Добавлена нормальная страница ошибки вместо стандартной Whitelabel.
6. Отчеты приведены ближе к образцам на фотографиях из задания.
7. В отчетах выводится время последнего действия по данным строки/месяца.
8. Ужесточено правило запрета визуальных дублей начислений и платежей.
9. Сальдо последующих имеющихся периодов автоматически пересчитывается после изменения исходных данных.
